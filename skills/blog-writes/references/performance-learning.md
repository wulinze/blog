# 性能类学习笔记的书写约定

适用于 CUDA、GPU、算子等性能机制与优化学习笔记；普通主题不必硬套瓶颈分类。

## 先建立术语和结构

- 术语按概念层级分组：瓶颈分类（bound）、warp/任务状态、统计指标各自成表；实现机制（tile、stage、overlap 等）在机制章节说明。bound 给范围、限制机制和判断证据，状态区分瞬时状态与发出事件，指标写单位、统计范围及分母。避免一张大表混装这些层次。

- 开篇先交代本篇会用到的术语、中文含义、观测对象及常见混淆，再展开机制。涉及性能瓶颈时区分 compute-bound、memory-bound、bandwidth-bound、latency-bound；解释术语的使用口径，不能把内存延迟与内存带宽混为一谈，也不能把这些标签当作始终互斥的分类。
- 先画清承载机制的结构。讲 SM 时先交代 warp 状态、调度/发出、依赖跟踪、寄存器、计算与访存通路，再解释 stall、occupancy 和 overlap。把“数据没好”和“队列/执行资源无法接收”分开；队列示意不伪装成未经证实的精确微架构。
- 依次串起“术语 → 结构 → 一次实际工作如何经过这些部件 → 为什么可能等待 → 对应优化”。性能标签必须附判断依据；high occupancy、long scoreboard、低带宽中的任何单项都不能独立证明根因。

## 图要能沿着读

- 每张图回答一个明确问题。图前说观察对象与目的；标明包含关系、请求/数据/控制箭头、时间方向，以及颜色或虚线的含义。只解释图中实际使用的编码。
- 图后用一个具体输入、warp 或 tile 顺着路径解释。并行时间线说明哪些动作独立、何时产生依赖、何时等待及何时才能复用 buffer。
- 标出教学假设、单位和硬件适用范围。示意宽度不冒充实测周期，软件分组不画成固定物理绑定，寄存器/shared/cache 不串成错误的必经层级。
- 本博客延续 Excalidraw 风格：发布可放大 SVG 及可编辑 `.excalidraw`，检查标签、箭头和手机布局。正文解释不能只藏在图里。

## 公式要能手算

- 先说明公式解决什么问题，再定义每个变量、维度与单位。矩阵首次使用 `@`/`.T` 时解释乘法/转置。
- 给推导：工作量为何相加，独立重叠为何取 max，资源约束为何取 min，整数分配为何 floor/ceil。随后代入小例子并解释结果。
- 区分恒等式、理论上界/下界、粗略估算与测量。容量取整、架构、缓存层级、流水线填充/排空、并行独立性等会改变结论的条件写在公式旁。
- 算术强度明确字节对应哪层内存；带宽和计算吞吐的单位、精度、指令类型保持一致。occupancy 的 warp 容量比例不等同算力利用率。
- 终端采用可直接阅读的纯文本公式；网页可使用既有公式渲染，但简单公式优先便于手算的写法。

## 优化与 demo

- 从原理到实现保持同一个例子：图中数据、tile/slot 编号、代码索引与 demo 输入要能互相对应。用“图上哪一步 → 哪段代码 → demo 怎样观察”说明 tiling 与 overlap，不能在前面讲完原理、后面孤立贴整段代码。SM 组成图和执行流程图区分：前者画包含、共享和依赖关系，后者画指令和数据如何推进。

- 每个优化说明改变了什么、作用于哪条通路、需要哪些条件及可能引入的代价。区分合并访存（跨线程地址）、tiling（分块/复用）与向量化（单线程访问宽度）。解释 async 提交、完成、可见性和 buffer 释放分别是什么。
- 用户要求可运行 demo 时提供完整源文件、必要头文件、编译运行命令、基线对照、错误检查和结果校验。涉及边界、对齐、矩阵尾块的代码必须处理或明确拒绝不支持的输入。网页贴出核心代码并提供完整源码，不能只交伪代码。
- 硬件专用机制可先给明确标为伪代码的协议图，但不能把它冒充可运行 demo。列出所需 GPU/Toolkit，编译通过、GPU 校验、性能实测分别报告；没有环境时如实标注，不生成虚构测速结果。
- 时延、带宽、性能倍数的教学模型与实测分开。计时要说明 warmup、重复次数、缓存/工作集和统计口径；检查正确性后再解释性能。最终优化目标是耗时/吞吐，不能只追求 occupancy 或某个 stall 比例。

## 性能分析流程与外部学习图

- 使用用户提供的性能决策图时，保留其调查顺序，但把经验阈值、特定架构实测和通用指标定义分开。流程按“热点与采集可信度 → 任务规模 → SOL/管线分流 → 调度/资源/分层访存证据 → 单项改动 → 正确性与耗时复测”形成闭环；每个分支注明下一项证据，不能用单一百分比自动定性或判定停止优化。
- 对 stall 与 memory 指标给出“含义 → 需核对的源码/指令/统计口径 → 候选动作 → 验证结果”。不要把 long scoreboard 等同 TMA、short scoreboard 等同 shared 冲突、local 访问等同 spill，或把 scalar 的 sector/request 基准直接套给向量化访问。
- SM/MEM 的 SOL 概览不等同 occupancy 或 DRAM 带宽；分层分析同时看吞吐、命中与访问放大。缓存命中低不自动意味着需要 tiling，Tensor 利用低也不自动意味着应该换 MMA。

## 连续学习材料的组织

- 用户的 `leetcuda-20261029.pdf` 学习系列采用“一章一篇独立博客”，严格按原文章节顺序继续创作；部分/分组仅用于导航，不合并成博客。编号接续已发布文章：CUDA 基础（一）、性能分析（二）、原文第二章 Roofline（三）、原文第三章归约（四），后续博客编号=原文章号+1。保留来源主题/PDF 页码及维护映射。全系列（含基础与目录）归入 `LLM 推理`，同步更新 LLM 栏目中的按编号入口。
- 学习路线覆盖后续主题，每项包含前置知识、学习目标、Triton 与 TileLang 练习和通过条件；明确“完整教程已发布”与“任务已梳理、待展开”，不发布空模板冒充完成内容。完整资料逐篇完善并发布。
- 每篇用同一小例子连接原理、公式、流程图、可运行 demo 和练习。练习提供输入输出契约、独立学生入口、提示、参考实现、边界校验与运行命令；架构专用机制按设备能力设计，不硬做 API 的一一对应。
- 逻辑读写、请求流量和具体内存层的实测字节分别记账；算法级理想流量不作为无条件的每次 DRAM 下界。不同精度的输入与输出分别计字节，计算屋顶匹配指令类型；特殊函数不能按任意 FLOP 系数直接套 FMA 峰值。

- 用户要求学习系列中的每个主题都带交互演示和具体代码 demo。交互需有可变输入/配置、可观察中间状态以及合适的单步/重置操作；demo 必须是完整源码、依赖、运行命令、最小输入、结果校验，不能只放代码片段、静态图或练习题名称。
- 路线中逐主题写明交互设计与代码 demo 任务，待制作与可运行成品区分；完整教程的发布检查包含这两项。架构专用主题提供 CPU 协议/索引/数值模拟与明确硬件条件的 GPU demo，分别报告验证状态，不能用模拟代替 GPU 实现交付。
