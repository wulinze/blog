# 性能类学习笔记的书写约定

适用于 CUDA、GPU、算子等性能机制与优化学习笔记；普通主题不必硬套瓶颈分类。

## 先建立术语和结构

- 开篇先交代本篇会用到的术语、中文含义、观测对象及常见混淆，再展开机制。涉及性能瓶颈时区分 compute-bound、memory-bound、bandwidth-bound、latency-bound；解释术语的使用口径，不能把内存延迟与内存带宽混为一谈，也不能把这些标签当作始终互斥的分类。
- 先画清承载机制的结构。讲 SM 时先交代 warp 状态、调度/发出、依赖跟踪、寄存器、计算与访存通路，再解释 stall、occupancy 和 overlap。把“数据没好”和“队列/执行资源无法接收”分开；队列示意不伪装成未经证实的精确微架构。
- 依次串起“术语 → 结构 → 一次实际工作如何经过这些部件 → 为什么可能等待 → 对应优化”。性能标签必须附判断依据；high occupancy、long scoreboard、低带宽中的任何单项都不能独立证明根因。

## 图要能沿着读

- 每张图回答一个明确问题。图前说观察对象与目的；标明包含关系、请求/数据/控制箭头、时间方向，以及颜色或虚线的含义。只解释图中实际使用的编码。
- 图后用一个具体输入、warp 或 tile 顺着路径解释。并行时间线说明哪些动作独立、何时产生依赖、何时等待及何时才能复用 buffer。
- 标出教学假设、单位和硬件适用范围。示意宽度不冒充实测周期，软件分组不画成固定物理绑定，寄存器/shared/cache 不串成错误的必经层级。
- 本博客延续 Excalidraw 风格：发布可放大 SVG 及可编辑 `.excalidraw`，检查标签、箭头和手机布局。正文解释不能只藏在图里。

## 公式要能手算

- 先说明公式解决什么问题，再定义每个变量、维度与单位。矩阵首次使用 `@`/`.T` 时解释乘法/转置。
- 给推导：工作量为何相加，独立重叠为何取 max，资源约束为何取 min，整数分配为何 floor/ceil。随后代入小例子并解释结果。
- 区分恒等式、理论上界/下界、粗略估算与测量。容量取整、架构、缓存层级、流水线填充/排空、并行独立性等会改变结论的条件写在公式旁。
- 算术强度明确字节对应哪层内存；带宽和计算吞吐的单位、精度、指令类型保持一致。occupancy 的 warp 容量比例不等同算力利用率。
- 终端采用可直接阅读的纯文本公式；网页可使用既有公式渲染，但简单公式优先便于手算的写法。

## 优化与 demo

- 每个优化说明改变了什么、作用于哪条通路、需要哪些条件及可能引入的代价。区分合并访存（跨线程地址）、tiling（分块/复用）与向量化（单线程访问宽度）。解释 async 提交、完成、可见性和 buffer 释放分别是什么。
- 用户要求可运行 demo 时提供完整源文件、必要头文件、编译运行命令、基线对照、错误检查和结果校验。涉及边界、对齐、矩阵尾块的代码必须处理或明确拒绝不支持的输入。网页贴出核心代码并提供完整源码，不能只交伪代码。
- 硬件专用机制可先给明确标为伪代码的协议图，但不能把它冒充可运行 demo。列出所需 GPU/Toolkit，编译通过、GPU 校验、性能实测分别报告；没有环境时如实标注，不生成虚构测速结果。
- 时延、带宽、性能倍数的教学模型与实测分开。计时要说明 warmup、重复次数、缓存/工作集和统计口径；检查正确性后再解释性能。最终优化目标是耗时/吞吐，不能只追求 occupancy 或某个 stall 比例。
