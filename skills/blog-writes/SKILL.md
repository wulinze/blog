# 博客写作

## 项目与入口

目标仓库为 `https://github.com/wulinze/blog`，本机默认路径 `/Users/wulinze/paper/blog`。先检查当前工作区与 `git remote -v`；若已在该仓库中，使用当前路径。读取仓库的 `AGENTS.md`（若有）、`README.md` 及待修改文件，保留用户的现有内容。

新建未完成笔记放在 `source/_drafts/`；正式文章在 `source/_posts/`；图片在 `source/images/`。模板资产和 skill 源码位于 `skills/blog-writes/`，不要把它们放进 Hexo 的 `source/` 目录。不要修改生成目录 `public/`。

## 选择笔记类型

按用户的学习对象和写作目的选择资产：

- **学习**：用户说“学习笔记”“原理”“结构”“理解算子”时，读取 [学习模板](assets/operator-learning.md)。从问题、数学定义、原理推导和内部结构入手，解释各部分的职责、依赖和数据流，再用一个小规模例子串起全过程。代码可用于解释思路，但不要求实现 kernel、运行 GPU、列性能表或安排调优实验。
- **实践**：用户说“实践笔记”“实现”“测试”“性能实验”“调优记录”时，读取 [实践模板](assets/operator-practice.md)。保留计算定义、参考实现、GPU 实现思路、正确性验证、实验条件和性能记录的结构。
- 两类都需要时，分别建文并互相链接；仅在对应文章已发布后添加公开页面链接，草稿间可先记录文件名。

**基础知识学习**是另一类笔记，不必套用单个算子的输入输出与推导结构。围绕“概念是什么、解决什么问题、如何工作、最小例子、常见误解”展开。用户正在整理初级 CUDA 知识；CUDA 基础笔记读取 [CUDA 学习模板](assets/cuda-learning.md)。可以写一篇总览，也可以按线程索引、内存、同步等单个主题拆篇。用到的前置术语先解释，区分编程模型与硬件执行；不要默认读者已理解 warp、SM、stream 或异步执行。代码用于说明概念，不强制要求跑性能实验或做 kernel 调优。

未指定类型的“算子笔记”默认先做学习草稿，并说明采用的类型。未指定具体算子且只要求模板时，生成可填写的通用模板，不替用户选择某个算子。只加载本次需要的资产。

## 性能主题：术语、图与公式

写 CUDA/GPU/算子性能机制或优化学习笔记时，读取 [性能学习书写约定](references/performance-learning.md)。开篇先解释相关术语与判断口径，讲清硬件结构再讲等待和优化；图交代阅读路径，公式交代变量、推导、单位、代入例子与适用边界。用户要求可运行 demo 时提供完整代码、校验与运行步骤，分别报告编译、GPU 运行及性能验证状态。

## 整本材料与连续学习系列

把 PDF、书籍或课程整理为多篇教程，或继续本用户的 LeetCUDA 系列时，读取 [学习系列交付约定](references/learning-series.md)。其中规定来源覆盖、章节粒度、编号分类、交互与代码、两类练习和发布验收。用户要求完整教程时，模板只是写作辅助，不能用模板中“代码可选”降低用户明确要求的交付范围。

## 写作与模板使用

复制选定资产到草稿目录，将 `{{ title }}` 替换为实际标题，`{{ date }}` 替换为创建时间。通用模板不预设 permalink，避免所有新文章共用一个地址；若用户已有 permalink，保持不变。为正式文章确定独立且稳定的 permalink。YAML 中的标题和摘要按需引用或转义。

学习笔记应把“计算什么”“为什么这样计算”“各部分如何组成整体”串成一条解释链。先给直觉，再定义符号，逐步推导，解释关键变换的依据；说明逻辑结构与实际代码组织的区别。小例子应与公式、形状和结构描述一致。根据具体算子增删章节，不强凑归约、矩阵乘法或并行策略等并不存在的结构。

以读者完成一个具体任务为目标：解释为什么、展示中间过程、让读者能改参数并校验结果。不能把章节摘要、术语罗列或反复套用的通用段落当作完整教程；各节展开本主题特有的机制、依赖、实现选择和易错点。学习目标写成可检验的动作，例如“能推导线程索引并校验尾块”，不只写主题名。

仅创建模板时保留填写提示；撰写具体文章时用有根据的内容替换提示。不把“待填写”模板描述成已完成文章。读取用户给出的材料、论文和源码后再写具体结论；版本相关或不确定的技术事实查阅原始论文、官方文档或对应源码，附直接来源链接。区分文献结论、推导、个人理解与待验证假设，不编造实测数据。

算子笔记分类为 `LLM 推理`，标签区分 `算子学习` 与 `算子实践`。本用户的 CUDA／LeetCUDA 连续学习系列统一分类为 `LLM 推理`（包括 CUDA 基础、性能分析、学习目录），在 `source/llm/index.md` 增加按编号排列的入口；标签使用 `CUDA` 和 `基础学习`，具体文章再补充主题标签。已有文章保持其合理分类。正文从 `##` 开始，不重复页面标题。中文叙述，术语首次出现说明含义；公式首次出现时解释变量和维度。

加粗、表格、代码块、公式与内嵌交互要检查实际页面；Markdown 源文件看起来正确不等于渲染正确。尤其检查中文加粗边界、长代码和宽表在手机上的显示。

博客 Markdown 最终经 KaTeX 渲染，可以使用 `$...$` 和独立行 `$$...$$`。终端回复中的公式使用行内代码或纯文本代码块；首次使用 `@` 和 `.T` 时说明矩阵乘法和转置。结构可先用文本数据流说明，复杂关系再补充已确认能在站点渲染的图。

## 检查、预览与发布

检查新草稿的 YAML、日期、分类、标签和 Markdown；仓库的 `./blog check` 主要检查正式文章，不能替代草稿检查。模板修改不需要运行 GPU 实验或整套浏览器测试。skill 自身有修改时，运行可用的 `skill-creator/scripts/quick_validate.py` 验证格式，并核对资产链接。

项目常用命令：

```bash
./blog dev                         # 含草稿的本地预览
./blog ready -- "文章标题"          # 将完成的草稿移入正式文章
./blog verify                      # 内容、测试、构建和链接检查
./blog sync -- "更新说明"           # 提交并上传源码
./blog publish -- "更新说明"        # 检查、提交源码并发布网站
```

根据本次请求及会话已有授权执行上传或发布；skill 的调用本身不额外授权远端操作，也不要求对已授权操作重复确认。只要求模板或草稿时，完成本地文件即可。`sync`/`publish` 会提交全部未忽略的改动，执行前检查工作区；若混有无关改动，按文件选择性提交后使用常规 Git 推送，不把无关内容一并提交。

正式发布前停止本次启动的预览进程，完成 `./blog verify`。只有已完成的文章才移入 `_posts`；已发布的算子文章在 `source/llm/index.md` 对应栏目添加入口，本用户的 CUDA／LeetCUDA 基础与目录同样加入 LLM 栏目，其他基础笔记按实际主题归档。源码上传与网站部署分别核对，不能把草稿已推送或 CI 构建成功当成文章已上线。认证失败或远端分叉时保留本地内容并报告具体阻塞，不强推覆盖。

交付时提供笔记或线上入口链接、已完成范围，以及本地草稿／源码已同步／网站已发布的实际状态。源码推送后核对站点部署和实际页面；有交互与下载时同时核对控件、资源和下载内容。
